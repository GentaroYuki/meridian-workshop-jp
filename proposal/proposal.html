1エグゼクティブサマリー

貴社のオペレーションチームは、毎日の業務を在庫ダッシュボードから始めています。ところが、その起点である概要ページの数字は、期間や拠点を変えても動きません。そのため現場はダッシュボードを信用できず、表計算ソフトで集計し直しています。また、自動テストがないため、IT 部門は変更を安全に承認できません。前任ベンダーが未完のまま残した作業によって、「直したいのに、直すことを承認できない」状態に陥っていると理解しています。

私たちの提案の軸は「確実に進める」ことです。

  1. 最初の3週間で、概要ページ（R1）を直します。現場が最も困っている数字の信頼を、まず取り戻します。
  2. 次に、テスト（R4）とアーキテクチャ資料（R5）を整えます。IT 部門が以後の変更を自信を持って承認できる土台を作ります。
  3. その土台の上で、Reports の改修（R2）と発注推奨（R3）を進めます。東京チームのための日本語対応（D2）も、ここで併せて提供します。

各フェーズの終わりには、動くものと完了基準を示してから次に進みます。価格は上限付きの T&M とします。Reports の欠陥は「少なくとも8件」とされており、全体の件数はまだ分かりません。それでも貴社が支払いの最大額をあらかじめ把握できるようにするためです。

2技術アプローチ

着手時のアーキテクチャレビュー（第1週）

前任ベンダーの引き継ぎメモは56行と簡素です。起動に必要な環境（uv、Node.js）すら書かれていません。そこで着手直後にコードを読み、メモと実装の食い違いを洗い出します。結果は R5 の土台にします。

R1 · 概要ページの改修

進め方
フィルターの値が API 呼び出しと集計処理まで届いているかを、画面からサーバーまで順に追います。原因を特定してから直し、KPI ごとの連動をテストで固定します。
リスク
原因が画面側とサーバー側の両方にまたがる可能性があります。第1週のレビューで範囲を確定させます。
完了基準
全 KPI がフィルターに連動すること。オペレーションチームが表計算ソフトの集計と突き合わせ、一致を確認できること。

R4 · ブラウザテストの自動化

進め方
標準的な E2E ツールを使い、「重要なフロー」を IT 部門・オペレーションチームと合意してから整備します。以後の改修では、必ずテストを先に追加します。
リスク
テストデータが不整合だと、テストが不安定になります。既存の JSON データの整合性も、併せて確認します。
完了基準
合意した主要フローの E2E テストが CI 上で安定して通ること。

R5 · アーキテクチャドキュメント

進め方
構成図、データの流れ、起動手順、既知の課題をまとめます。フェーズ2で初版、フェーズ4で最終版を納品します。
完了基準
貴社 IT 部門がこの資料だけを見て、環境を立ち上げて変更を判断できること。

R2 · Reports モジュールの改修

進め方
貴社が記録した8件を出発点に全面調査を行い、欠陥一覧を確定・合意してから修正します。1件ごとに回帰テストを追加します。
リスク
件数が8件を大きく超える可能性があります。上限額の範囲内で、優先順位を貴社と決めます。
完了基準
合意した欠陥一覧のすべてが解消され、テストで確認済みであること。

R3 · 発注推奨機能

進め方
現在庫、需要予測、予算上限から推奨を出す Restocking ビューを追加します。推奨ロジックは Tanaka 様のチームと試作で早めに確認します。
完了基準
予算上限を入力すると、根拠つきの推奨一覧が表示され、受け入れ確認を済ませていること。

D2 · 国際化対応

進め方
既存の i18n の仕組みを残りのモジュールへ広げ、東京チームに実際の画面で確認してもらいます。
完了基準
全モジュールで日本語と英語を切り替えられること。
